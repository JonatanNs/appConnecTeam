6 - Organisation du code : architecture par fonctionnalités (feature-based)​

Le frontend est organisé par fonctionnalité métier (feature) plutôt que par type de fichier. Chaque module (ex: messaging, notifications, auth) regroupe ses propres composants, services et interfaces.

Cette organisation permet :

  • une meilleure lisibilité et navigation dans le code ;
  • un couplage plus faible entre les fonctionnalités ;
  • une évolution plus simple du projet (ajout, modification ou suppression d'une fonctionnalité sans impacter les autres) ;
  • une cohérence avec l'architecture backend, elle aussi organisée par fonctionnalités.

7 - Réactivité avec les Signals​

L'application utilise les Signals d'Angular (signal, computed, effect, toSignal) comme mécanisme principal de gestion d'état et de réactivité, plutôt qu'une gestion manuelle avec des Subject/BehaviorSubject exposés directement dans les composants.

Cette approche permet :

  • une détection de changement plus fine et performante (zoneless-ready) ;
  • un code plus lisible et déclaratif ;
  • une intégration native avec RxJS via toSignal/toObservable pour combiner flux HTTP et WebSocket ;
  • une meilleure gestion du cycle de vie des abonnements (nettoyage automatique).

8 - Communication HTTP et temps réel​

L'application combine deux modes de communication avec le backend :

  • HTTP (REST) via HttpClient, pour les opérations classiques (récupération de données, création, modification, suppression) ;
  • WebSocket (STOMP) via @stomp/stompjs, pour la communication en temps réel (messagerie instantanée, indicateur de saisie, notifications).

Les données provenant de ces deux sources sont fusionnées via RxJS (merge, scan) puis exposées sous forme de Signals aux composants, assurant une source de vérité unique et réactive.
